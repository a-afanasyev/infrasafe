# Миграции — контекст для Claude Code

Этот файл загружается только при работе с файлами в `database/migrations/`.
Перенесено из корневого `CLAUDE.md` (2026-08-13) — там оно лежало резидентно
в каждой сессии, включая те, что базы не касаются.

Пошаговый регламент раннера — в `README.md` рядом. Здесь то, чего в README нет:
почему отдельные миграции выглядят именно так.

## Раннер (AUD-002, LIVE на проде с 2026-06-12)

Источник истины — таблица **`schema_migrations`** (`filename` PK + `checksum`) с
row-mutex `migrate_lock`. **`scripts/migrate.sh`** запускается с хоста через
`docker compose exec`, НЕ внутри неизменяемого образа приложения, и берёт
миграции из **закреплённого `MIGRATE_TARGET_COMMIT`** (git blob, не рабочая
копия → нет TOCTOU).

Подкоманды: `status` (применённые/ожидающие/дрейф + инвариант ACL; выход 2 =
нет `schema_migrations`, fail-close; 5 = дрейф), `up` (применить ожидающие под
локом; **каждая миграция владеет своей транзакцией** — раннер НЕ оборачивает,
иначе `CREATE INDEX CONCURRENTLY` из 007 не сработает), `baseline` (разовая:
создать таблицы раннера, проверить матрицу сигнальных объектов и отметить
замороженный список **003-034** применённым без выполнения — для прода,
мигрированного руками), `force-unlock`, `repair-acl`.

Чистая логика discovery/checksum/allowlist — `scripts/lib/migrate-discover.js`
(покрыта jest-юнитами); статическая преамбула baseline — `scripts/lib/baseline-prelude.sql`.

**ACL:** `ALTER DEFAULT PRIVILEGES` из 017 автоматически выдаёт runtime-роли DML
на новые таблицы → раннер делает REVOKE на своих таблицах после каждого `up`
(идемпотентно, в cleanup-trap; провал REVOKE на успешном пути → `up` возвращает
ненулевой код).

**Чистый bootstrap:** `database/init/99_schema_migrations_baseline.sql`
самодекларирует 003-017 (их запекают init 01-09), `up` доделывает 018+.
Единый `database.sql` намеренно НЕ несёт манифеста (неполный legacy-снимок) →
fresh-unified закрывается по fail-close by design.

**Выкатка:** зашита в `update-production.sh`, `MIGRATE_WIRING_ENABLED=true`.
Порядок: fetch → guard `merge-base --is-ancestor` → deploy-guard на изменения
самого раннера → `status` → `up` (схема ДО переключения приложения) →
`git merge --ff-only`.

**Только вперёд** (AUD-043): применённые миграции неизменяемы (правка →
дрейф контрольной суммы → abort); 035+ обязаны быть транзакционными и
обратносовместимыми (expand-only).

E2e: `npm run migrate:test` (эфемерный postgres, `tests/migrate/`).

Правки бэкенда по-прежнему требуют пересборки образа (SEC-14); раннер живёт на
хосте и пересборки не требует.

**Прод-особенность:** на прод-хосте НЕТ node → раннер гоняет discovery через
образ приложения (`MIGRATE_NODE_MODE=auto`, резолвится через
`docker compose images -q`, НЕ через `config --images`). Сигнальные объекты
003/008/009/021 приведены к реальности canonical-bootstrap: прод поднимался из
`database.sql`, а не линейным применением. См. память
`prod-migration-runner-baselined` — повторно эти миграции не запускать.

## Почему отдельные миграции такие

Полный список — в `README.md` («Список миграций»). Ниже только решения, которые
из самих `.sql` не читаются.

- **036 + 037 — канонизация трансформеров (AUD-039), фазы EXPAND и CONTRACT.**
  036 добавляет колонки в `transformers`, переносит 4 живые строки из legacy
  `power_transformers`, перецепляет здание 5 → Олмазор-1, убирает тестовую
  строку «1111» и добавляет INTEGER-перегрузку `find_nearest_buildings_to_transformer`.
  037 дропает `power_transformers`, `buildings.power_transformer_id`, FK и
  VARCHAR-перегрузки — **и чинит регрессию арности из фазы 1**: создаёт
  правильную 3-аргументную INTEGER `find_nearest(id, radius, limit)`, которую
  зовёт модель, и дропает ошибочную 2-аргументную из 036. 037 — намеренно
  CONTRACT-миграция, цель отката = образ фазы 1.

- **038 — `uk_requests`** (контракт УК от 2026-07-23): реестр заявок,
  созданных на стороне УК (бот/дашборд), которым нет места в `alert_request_map`
  (там `alert_id NOT NULL`). Ключ upsert — `uk_request_number`; инвентарь и
  счётчики карты обслуживают ARM ∪ uk_requests.

- **039 — расширение ARM + архив** (2026-07-24): `uk_request_number`
  VARCHAR(20)→(50) — валидатор принимал 50, а `markSent` отдавал 500 на 21-м
  символе. Плюс колонка `archived_at` и архивация 7 подтверждённых УК
  осиротевших синтетик на infrasafe; архивные строки скрыты из инвентаря и
  счётчиков через `archived_at IS NULL`, аудит сохранён. На profk и на чистой
  базе — no-op.

- **040 — CHECK на `water_lines.status`** (M-12b / PR-2b): `active|maintenance|inactive`,
  NULL разрешён явно (колонка nullable с DEFAULT 'active'). Вторая половина
  M-12: PR-2 закрыл сторону ПРИЛОЖЕНИЯ (`WaterLine.assertValidStatus` на всех
  5 путях записи), а база всё ещё принимала любую строку ≤20 символов.
  Ограничение сразу VALID, не NOT VALID — `water_lines` пуста на обоих продах
  (проверено 2026-07-25), сканировать нечего. Это CONTRACT, а не expand-only:
  выезжает своим релизом ПОСЛЕ PR-2, чтобы образ отката уже нёс тот же whitelist.

- **041 — сезонное окно `alert_rules`** (B-009): `season_from`/`season_to` как
  `CHAR(5)` `'MM-DD'` — **повторяющиеся, без года** (DATE молча протухал бы
  каждое 1 января). Оба NULL = круглый год, и это значение по умолчанию у
  каждой существующей строки → сама миграция поведения НЕ меняет; окно включает
  оператор из админской панели «Правила эскалации». Переход через Новый год —
  ОСНОВНОЙ случай, а не краевой (отопительный сезон 10-15..04-15), см.
  `checkSeasonGate`. CHECK'и на формат и на парность (одно поле без второго
  отвергается). Expand-only.

- **042 — домен `controllers.status`** (AR-21): CHECK `online|offline|maintenance`
  плюс DROP/CREATE `mv_transformer_load_realtime` с `c.status = 'online'` —
  представление считало `'active'`, значение из домена ТРАНСФОРМАТОРОВ, поэтому
  `active_controllers_count` был ВСЕГДА 0. CONTRACT, выезжает после whitelist'а
  на стороне модели, чтобы образ отката уже отвергал значения вне домена.

- **043 — `users.sessions_revoked_at`** (M-6): отсечка массового отзыва сессий.
  Работает в паре с `password_changed_at` из 016 — `_isIssuedBeforeCutoff`
  берёт МАКСИМУМ из двух, поэтому отзыв достаёт разом до всех трёх веток
  middleware, refresh- и 2FA-временных токенов. Метка времени, а не
  `token_version`: `iat` есть в каждом токене по спецификации, а новому claim'у
  понадобился бы ответ на вопрос об уже выданных токенах, где его нет.
  NULL = отсечки нет = сегодняшнее поведение → expand-only, сама миграция не
  меняет ничего.
