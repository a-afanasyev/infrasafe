## Контекст

Исторический/планировавшийся контур подключения контроллеров:

```
Контроллер → VPN → MQTT (Mosquitto) → InfluxDB (хранение TS)
                                    → Node-RED (подготовка) → INSERT напрямую в PostgreSQL
```

Фактический работающий контур (код в этом репо):

```
Генератор → HTTP POST /api/metrics/telemetry → metricService → PostgreSQL
```

Вводные, зафиксированные 2026-07-07:
- Реальных контроллеров пока нет / единицы; контур строится **для новых** подключений.
- Горизонт 12 месяцев: **50–200 контроллеров**, штатная частота — 1 агрегированный замер/мин с устройства.
- **Нужен канал управления «вниз»** (config push, перезагрузка, прошивки, отладка).
- Диск прода расширен до **40 ГБ** (было 20, впритык — см. memory `prod-disk-tight-deploy-builder-cache`).
- Требование продукта: графики телеметрии на исторических интервалах (день/неделя/месяц/год).

Критический факт, определяющий решение: вся событийная логика системы повешена на
вход метрик через бэкенд — `metricService.createMetric` эмитит `LEAK_CHECK` /
`VOLTAGE_CHECK` / `HEATING_CHECK` (B-005), дальше persistence-гейты →
`createAlert` → outbox → заявка в УК → верификация → reopen (Sprint 9–11,
AUD-001/006). Метрика, записанная в таблицу **мимо** бэкенда, для всего этого
конвейера невидима: протечка попадёт в БД и на график, но алерт не родится и
заявка в УК не уйдёт. Также прямая запись обходит валидацию, SEC-25 allowlist
полей и least-privilege роль `infrasafe_runtime`.

## Решение 1 — контур приёма

```
Контроллер (за NAT/LTE)
   │ WireGuard-туннель (host-level wg0, НЕ в Docker)
   ▼
Mosquitto — слушает ТОЛЬКО на wg-интерфейсе; per-device credentials;
   │         topic-ACL: контроллер X публикует только в telemetry/X/#
   │ telemetry/<controller_id>, QoS 1, LWT → online/offline статус
   ▼
mqtt-bridge — НОВЫЙ тонкий Node.js-сервис в этом репо
   │           (паттерн ukOutboxService: singleton, env-gated, тесты)
   ▼
POST /api/metrics/telemetry — единственная дверь входа телеметрии (как сейчас)
   ▼
metricService → PostgreSQL + весь событийный конвейер алертов
```

Канал «вниз»: команды/конфиг — publish бэкенда в `cmd/<controller_id>` через тот
же Mosquitto (bridge уже держит соединение); тяжёлое (прошивки, reverse SSH,
отладка) — напрямую по VPN.

**Принято:** WireGuard (обязателен), Mosquitto (при появлении реальных
контроллеров), in-repo mqtt-bridge.
**Отклонено:** Node-RED (логика вне git/тестов/ревью, дублирует code-based
обработку), **прямые INSERT в PostgreSQL из чего бы то ни было, кроме
бэкенда — запрещены** (обход алерт-движка, см. контекст).

Follow-ups контура приёма (фиксируются здесь, имплементация — отдельной спекой
при подходе реальных контроллеров):
- `telemetryLimiter` ключуется по IP (`rateLimiter.js`) — bridge сольёт все
  контроллеры в один IP; нужен служебный ключ для bridge либо ключевание по
  `controller_id`.
- Агрегация на краю: контроллер (industrial PC) усредняет сам до 1 замера/мин;
  сырые высокочастотные данные не покидают устройство.
- Provisioning WG-ключей при 50+ устройствах — скрипт или Headscale.
- Идентичность: MQTT client-id ↔ `controllers.controller_id`.

## Решение 2 — хранение временных рядов

**Отдельный time-series движок НЕ вводится.** Вводится time-series **модель
данных** в существующем PostgreSQL — три яруса с downsampling'ом:

| Ярус | Таблица | Гранулярность | Retention | Объём при 200 ctrl |
|---|---|---|---|---|
| 0 | `metrics` (нативные месячные партиции по `timestamp`) | сырьё, 1/мин | **90 дней**, `DROP PARTITION` | ~8.5 ГБ скользящих |
| 1 | `metrics_hourly` | avg/min/max за час | **3 года** | ~0.6 ГБ/год |
| 2 | `metrics_daily` | avg/min/max за день | **навсегда** | ~25 МБ/год |

Роутинг чтения для графиков (форма ответов API не меняется, фронт не трогаем):
≤ 48 ч → raw; 2–60 дней → hourly; > 60 дней → daily. График шириной ~800 px
показывает ~800 точек — годовой график из daily-яруса полноразрешённый по
определению; хранение сырья годами ради него избыточно (это ровно тот
downsampling, который TSDB делают внутри себя).

min/max храним наряду с avg: короткие события (просадка напряжения на 30 сек)
видны в hourly-min, но исчезают в hourly-avg; графики рисуют avg линией,
min/max — лентой.

Rationale против отдельной TSDB (InfluxDB): на 200 ctrl × 1/мин = **~3.3
insert/sec** — на три порядка ниже порога, где PostgreSQL становится узким
местом; Influx не умеет JOIN со `buildings`/`controllers` (вся аналитика всё
равно в PG); второй stateful-сервис = второй бэкап, вторые апгрейды, вторая
точка отказа; данные дублируются. Вердикт дебата 2026-04-02 подтверждён.

**TimescaleDB — осознанно отложен** (это расширение того же PG, не вторая
база). Причина отложить: требует смены образа БД (`postgis/postgis` →
`timescale/timescaledb-ha`) на живом baselined-проде — несоразмерный риск для
текущего масштаба, при том что все нужные паттерны (партиции, worker,
SECURITY DEFINER обёртки) в репо уже обкатаны. Триггеры пересмотра:
- устойчиво > 500–1000 insert/sec (≈ секундные замеры или ≥ 30 тыс. устройств), ИЛИ
- бизнес-требование хранить сырьё > 1 года, ИЛИ
- давление диска, при котором колоночная компрессия (10–20×) дешевле апгрейда диска.

Путь апгрейда не сгорает: модель данных идентична, конверсия партиционированной
таблицы в hypertable и rollup'ов в continuous aggregates — механическая.

## Бюджет диска (40 ГБ)

| Статья | Оценка |
|---|---|
| ОС + Docker (images, builder cache — чистить перед деплоем!) + логи | ~10–12 ГБ |
| UK-стек на том же хосте (uk-postgres и пр.) | ~2–4 ГБ |
| PG кроме телеметрии | < 1 ГБ |
| Телеметрия steady-state при 200 ctrl (raw 90д + hourly 3г + daily) | ~10–12 ГБ |
| **Свободный запас** | **~12–15 ГБ** |

Рычаг при давлении: raw retention 90 → 60 дней (−3 ГБ) без потери графиков
(hourly покрывает). Обязательный follow-up: мониторинг диска с алертом на 80 %.
Открытый вопрос: где лежат pg_dump-бэкапы — если на том же диске, учесть.

## Последствия и принятые издержки

1. **FK `fk_alerts_metric` (миграция 021) снимается** — партиционированная
   таблица не может быть целью FK на неполный уникальный ключ.
   `alerts.metric_id` становится soft-reference (как `related_request_number` и
   прочие). Побочно это же разблокирует retention: `DROP PARTITION` не будет
   блокироваться ссылками, и исчезает неочевидный `ON DELETE CASCADE`
   (удаление метрики молча удаляло алерт).
2. PK `metrics` становится составным `(metric_id, timestamp)`; глобальная
   уникальность `metric_id` обеспечивается sequence (bigserial), как и всюду.
3. Триггер `trig_update_heartbeat` переезжает на партиционированный parent
   (детали двойного срабатывания — в спеке).
4. Аналитика последних минут/часов (persistence-гейты, верификация, freshness
   probes AUD-001) не меняется: их окна (секунды–600 сек) на порядки внутри
   raw-retention, фильтры `controller_id + timestamp` дают partition pruning.
5. Появляются два фоновых процесса по обкатанному паттерну (`mvRefreshService`):
   rollup-агрегация и партиционный maintenance (создание вперёд + retention),
   оба через SECURITY DEFINER обёртки (runtime-роль не владеет таблицами —
   паттерн миграции 020).

## Отклонённые альтернативы (сводка)

| Альтернатива | Почему нет |
|---|---|
| InfluxDB рядом с PG | Дублирование данных, нет JOIN, второй stateful-сервис; выигрыша на этом масштабе нет |
| Node-RED как ETL | Логика вне git/тестов; главное — прямой INSERT ломает алерт-конвейер |
| TimescaleDB сейчас | Смена образа живой baselined-БД ради 3 insert/sec; отложен с явными триггерами |
| Хранить всё сырьё вечно без ярусов | 35 ГБ/год при 200 ctrl на 40 ГБ диске; графикам не нужно |
| pg_cron для rollup/retention | Логика вне git и вне тестов; в репо принят паттерн in-app singleton worker |
