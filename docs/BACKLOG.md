# Единый беклог InfraSafe

**Сведён 2026-08-10.** Отменяет как самостоятельные источники:

- `AUDIT_REPORT.md` (6 августа) — ID вида `AR-` / `CO-` / `DE-` / `SE-` / `EN-`
- `docs/audit/sprint-11-backlog.md` (25 июля) — ID вида `M-` / `R2-` / `L-` / `B-` / `AUD-`

`sprint-11-backlog.md` остаётся в репозитории как доказательная база. С
`AUDIT_REPORT.md` иначе: он в `.gitignore` (строка 129) как «вывод скилла
`/audit`, перегенерируется каждый прогон, хранится локально» — то есть **никогда
не был закоммичен**. Августовские находки живут только на машине, где запускался
аудит, и исчезнут вместе с ней.

Поэтому здесь у каждого пункта есть не только ссылка, но и описание сути:
файл должен быть самодостаточным, а не оглавлением к чему-то, чего в репозитории
нет. Обоснования и разбор по-прежнему стоит смотреть в исходных отчётах, если
они под рукой.

## Зачем сведение

Не потому, что списки дублируют друг друга. Августовский аудит читал июльский
заранее, намеренно не переописывал его открытые пункты и взял непересекающееся
пространство идентификаторов — это сказано в его шапке и выдержано. Немногие
совпадения (`AR-8` ↔ `M-2`/`B-003`, `EN-6` ↔ `R2-37`, `AR-3(б)` ↔ `R2-04`/`AUD-008`)
он сам и помечает ссылками на старые ID.

Проблема в другом: **открытое множество не лежит целиком нигде**.

- Июльский список не обновлялся с 25 июля. Шесть его пунктов закрыты августовской
  и последующей работой, и там это не отмечено — список завышает объём.
- Августовский отчёт по построению содержит только новое, то есть заведомо неполон
  как рабочая очередь: двадцать шесть июльских пунктов в него не входят по замыслу.
- Ни один из двух не знает про приоритеты другого. «P1» августовского и «P1»
  июльского — разные шкалы, сравнить их можно только вручную.

Поэтому здесь не третий аудит, а сложение двух с перепроверкой каждой ссылки
и единой шкалой приоритета. Новых находок в этом файле нет — кроме одной
пометки про `sendSuccess`, всплывшей при сверке.

## Легенда

**Приоритет.** `P1` — берём сейчас. `P2` — очередь. `P3` — по касанию.
`P4` — заморожено до наступления условия (вторая реплика, телеметрия, решение владельца).

**Труд.** `XS` — минуты. `S` — один короткий PR. `M` — PR с дизайном. `L` — дробится.

10 августа 2026. Где адрес изменился с момента заведения — указан новый.

## Контекст: что вообще под нагрузкой

Беклог взвешивался по риску в коде. Вот что на площадках на 10 августа:

| | profk | .105 |
|---|---|---|
| здания | 30 | 8 |
| трансформаторы | **0** | 4 |
| контроллеры | **0** | 2 |
| метрики | таблица пуста | нет с 16 июня |
| события УК | 25 за 3 суток, все `success` | нет с 23 июля |

На главной площадке живёт только интеграция с УК. Энергетическая часть —
представление, аналитика нагрузки, проверки напряжения, определение offline —
обслуживает пустой набор данных. Шесть пунктов (`AR-6`, `AR-8`, `AR-17`, `AR-20`,
`AR-21`, `DE-7`) описывают код, который сегодня не может сработать по отсутствию
входных данных. Два из них (`AR-21`, `AR-17`) от этого не менее срочны, а более:
они привязаны к дате подключения железа.

## План реализации

### Волна A — сведение и дешёвая уборка

Один PR. `CO-8`, `DE-8`, `R2-34`, комментарий к `sendSuccess`, удаление
`docs/internal/tasks.md`; в `AUDIT_REPORT.md` и `sprint-11-backlog.md` — шапка
«актуальный список в `docs/BACKLOG.md`» и простановка закрытого.

Делается первой не потому, что важна, а потому что до неё каждый следующий разбор
платит за переоткрытие уже известного.

### Волна B — admin-слой

`AR-3(б)` + `Новое №8` **одним PR**, порядок внутри жёсткий: сперва разбор статуса
в catch, затем перевод на модели. Иначе типизированные 4xx моделей окажутся
проглочены. Попутно снимается `AR-3(в)` — `adminQueryBuilder` остаётся только под
листинги. Закрывает три ID из двух источников сразу.

### Волна C — валидация, пачка S-размера

`CO-7`, `L-6`, `L-7`, `AR-11`. Общая тема: вход не проверяется там, где должен, и
отказ приходит как 500 вместо 4xx. Правильные образцы для всех четырёх уже есть в
репозитории — это перенос дисциплины, а не изобретение.

### Волна D — гарантии окружения

`AR-9` + `M-7`/`M-11` + `EN-6` одним узлом: `env.js` начинает валидировать значения,
`REDIS_URL` становится обязательным или проверяется в preflight деплоя,
`.env.example` перестаёт умалчивать о двух переменных. Разносить бессмысленно —
это три симптома одного пробела.

### Волна E — до приезда железа

`AR-21` и `AR-17`. Срок задаёт не беклог, а ADR #138: обе дыры проявятся в первый
день работы телеметрии. Планировать по факту решения по ADR.

### Волна F — сессионный слой

`M-5` (S, самостоятельна) → `M-6` (требует `token_version`) → `M-4` (требует решения,
что делать с secret и recovery-кодами при self-service setup). Именно в этом порядке:
`M-5` дёшева и независима, `M-6` даёт примитив, на который потом опирается `M-4`.

### Волна G — тестовая инфраструктура

`STAGING-VM` + `Новое №4` (решение: завести конфиг и поднять VM либо честно
записать, что staging'а нет), затем `R2-14` и `R2-24`. Пока staging'а нет, каждый
деплой идёт сразу в оба прода — это фон для всего остального в списке.

### Вне волн

Решения владельца (`M-20`, `DE-6`, `Новое №5`, судьба staging) не требуют кода и
могут быть приняты в любой момент — они разблокируют соответствующие пункты.
Шаги с sudo на .105 независимы от всего.

### Чего делать не следует

Спекулятивный рефакторинг alert/UK-домена: ядро работает, покрыто тестами, уже
пережило один разбор (`AUD-012`). Дробление `admin.js`/`script.js` до появления
модульного графа. Разморозка `P4` без наступления условия — там нет ни одного
пункта, который проявляется при одной реплике и пустой телеметрии.
