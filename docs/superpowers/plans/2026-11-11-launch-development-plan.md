## 3. Архитектурные решения

### 3.1. Приёмный контур

```
устройство (STM32) ──Zigbee / LoRa──▶ шлюз (мини-ПК на Linux)
   шлюз ──MQTT поверх WireGuard──▶ Mosquitto на площадке
   Mosquitto ──▶ mqtt-bridge (в репозитории InfraSafe)
   mqtt-bridge ──POST /api/metrics/telemetry (HMAC)──▶ app ──▶ тревоги ──▶ outbox ──▶ УК
```

Это ADR от 07.07.2026 без изменений по существу. Прямая запись в БД мимо
`/metrics/telemetry` по-прежнему запрещена: она обходит движок тревог.

### 3.2. Шлюз

**Пилот — Wiren Board.** Контроллер уже на руках и закрывает весь состав пилота:

- счётчики и измерители по Modbus (RS-485) — напряжение и ток по фазам;
- датчики давления и температуры через его модули ввода;
- датчики протечки по Zigbee или проводные;
- собственный MQTT-брокер, темы вида `/devices/<устройство>/controls/<канал>`.

До площадки — WireGuard, MQTT только внутри туннеля. Со стороны сервера нужен
один адаптер формата тем Wiren Board.

**Дальше — мини-ПК на Linux** как дешёвый шлюз для массовой установки:
Zigbee2MQTT для Zigbee и ChirpStack для плат LoRaWAN. Каждый источник —
отдельный адаптер моста, контракт телеметрии общий.

Контроллеры на ESP32 (Kincony, Lavritech) публикуют в MQTT сами и подключаются
к тому же брокеру без шлюза — там, где есть Ethernet или Wi-Fi.

Свою плату шлюза на STM32 не делаем: стек TCP/TLS/MQTT пришлось бы писать и
отлаживать самим, а готовые Zigbee2MQTT и ChirpStack там недоступны.

### 3.3. Ключи (пересмотр N-20)

Исходная постановка N-20 — ключ подписи на каждый контроллер. Устройства на
LoRa и Zigbee HTTPS с подписью не умеют, поэтому:

- учётная запись MQTT и ACL — на **шлюз** (`telemetry/<gateway_id>/#`);
- устройство опознаётся парой «шлюз + аппаратный адрес» (IEEE или DevEUI) и
  должно быть заведено в системе; неизвестное попадает в карантин, а не создаётся само;
- сервисный HMAC-ключ один — у моста.

Компрометация шлюза затрагивает только его устройства; отзыв — одна запись в Mosquitto.

### 3.4. Модель данных

- Таблица `metrics` и существующие проверки (напряжение, нагрузка, тепло,
  протечка) **не трогаются** до приёмки. Движок покрыт тестами и прошёл несколько аудитов.
- Новые типы устройств идут в универсальную модель: `gateways`, `device_types`
  (описание каналов: имя, единица, вид, диапазон), `devices`, `device_readings`
  (узкая таблица, месячные секции), `device_state` (текущее состояние).
- Объединение двух путей — после приёмки. Потолок решения: два пути записи
  показаний живут параллельно; условие объединения — стабильная работа
  универсального пути не менее месяца.

### 3.5. Интерфейс и карта

- Рабочее место оператора — раздел «Мониторинг» в панели УК (React, общая
  дизайн-система, RU/UZ, роли УК). Работает поверх REST API InfraSafe.
- `admin.html` остаётся инструментом настройки для администратора. Его не
  переписываем и не дробим.
- Публичная карта `/map` остаётся на infrasafe.uz как демо.
- **Карта одна.** Реестр дворовых ассетов ведёт УК (по его ТЗ), на карте
  мониторинга ассеты — отдельный слой. Фонарь с контроллером — ассет,
  связанный с устройством через `devices.uk_asset_id`.

### 3.6. Единый вход

Edge-nginx на запрос к API InfraSafe спрашивает УК, кто пользователь
(`auth_request`), и передаёт приложению идентификатор и права в заголовках,
подписанных общим секретом edge ↔ app. Входящие заголовки с такими именами от
клиента edge срезает. В УК добавляются права `monitoring.view`,
`monitoring.manage`, `monitoring.control`. Режим задаётся `AUTH_MODE=uk|local`.

## 5. Порядок работы

- Один пакет — одна ветка и один PR. Прямых коммитов в `main` нет.
- Весь новый SQL проверяется на живом Postgres (`npm run test:db`), не на моках.
- Выкатка: сначала .105, сутки наблюдения, затем profk. Бэкенд — через
  `update-production.sh` с пересборкой образа; nginx — `nginx -t` на целевом хосте.
- Пакеты в репозитории УК — отдельными PR там, по его правилам (`make test-ci`,
  сборка обоих брендов).
- Новое поведение включается флагом и по умолчанию выключено.
- Статус пакетов ведётся в `docs/BACKLOG.md`, раздел «Сейчас: до запуска InfraSafe».

## 7. Программа приёмки — черновик

1. Показание реального устройства появляется на карте не позже чем через 60 секунд.
2. Выход напряжения за порог создаёт заявку в панели УК не позже чем через минуту.
3. Протечка создаёт заявку аварийной срочности.
4. Возврат параметра в норму закрывает тревогу; повторная авария открывает заявку снова с пометкой.
5. Устройство без связи дольше заданного времени отмечается и даёт заявку инженеру.
6. Сотрудник УК входит один раз и видит раздел «Мониторинг» согласно своим правам.
7. Диспетчер видит ленту тревог, карту и карточку объекта на компьютере и телефоне.
8. График показаний по дому доступен за сутки, неделю и месяц.
9. Новый тип устройства подключается настройкой, без изменения программы.
10. Неизвестное устройство не попадает в систему без подтверждения администратора.
11. Администратор меняет пороги; изменение сохраняется в журнале с автором.
12. Отчёт за месяц показывает число тревог и время реакции по каждому дому.
13. Интерфейс оператора доступен на русском и узбекском.
14. Перезапуск сервера не теряет показания и не дублирует заявки.
15. Система восстанавливается из резервной копии по инструкции.
16. При недоступности панели УК показания продолжают приниматься, заявки доходят после восстановления.
