## 1. Правило отбора

Модуль переделывается, только если без этого нельзя подключить устройства,
дать оператору рабочее место или пройти приёмку. Всё остальное до 30.12
остаётся как есть, даже если выглядит неидеально.

Судьба модуля — одно из пяти:

- **без изменений** — не трогаем до приёмки;
- **доработка** — добавляем поведение, структура остаётся;
- **переделка** — меняем устройство модуля;
- **новый** — модуля нет, создаём;
- **вывод** — перестаёт быть основным путём, остаётся как запасной или удаляется.

## 3. По группам

### 3.1. Приём телеметрии

**Новое.**

- **Шлюз.** Каталог `gateway/`: конфигурация WireGuard, Zigbee2MQTT, публикация
  в брокер, инструкция сборки. Кода приложения здесь нет — это образ и настройки.
- **Mosquitto.** Сервис в `docker-compose.unified.yml`. Слушает только интерфейс
  туннеля, учётная запись и права на темы — на шлюз.
- **`mqtt-bridge`.** Отдельный процесс в том же образе приложения, по образцу
  `ukOutboxService`: подписка, нормализация, отправка в `/api/metrics/telemetry`
  с подписью, повтор с нарастающей задержкой, журнал отброшенного. Адаптеры
  входных форматов — по одному файлу на источник: родной контракт, Zigbee2MQTT,
  позже ChirpStack. Устройства на LoRa и Zigbee различаются только адаптером.

**Доработка.**

- **`metricService.processTelemetry`.** Проверка по контракту v1: единицы,
  физические диапазоны, версия. Сегодня диапазоны не проверяются.
- **`telemetryHmac` и лимит.** Сервисный ключ остаётся один, у моста. Лимит
  считается по шлюзу, а не по IP: за мостом все устройства приходят с одного адреса.
- **`generator/`.** Режим публикации в MQTT рядом с существующим HTTP — чтобы
  симулятор шёл тем же путём, что и железо.

**Не трогаем.** Сам маршрут `/metrics/telemetry` и события, которые
`metricService.createMetric` публикует для проверок напряжения, тепла и протечки.

### 3.2. Устройства и хранение

**Новое.**

- Таблицы и модели `gateways`, `device_types`, `devices`, `device_readings`,
  `device_state`. Тип устройства описывается данными: список каналов с единицей,
  видом (показание, состояние, счётчик) и диапазоном.
- `deviceService`: приём показания универсального устройства, обновление
  состояния, отметка последней связи, карантин неизвестных.
- Сервис свёрток: часовые и суточные агрегаты, выбор уровня по длине периода.

**Переделка.**

- **`Metric` и очистка.** Таблица `metrics` переводится на месячные секции;
  `cleanupOldMetrics` с удалением запросом заменяется удалением секций. Перед
  этим снимается внешний ключ тревог на метрику — он несовместим с секциями
  (разобрано в ADR от 07.07).

**Доработка.**

- **`controllerStatusScheduler`.** Сегодня отмечает «не на связи» только
  контроллеры. Добавляются устройства, батарея и уровень сигнала; результат —
  тревога инженерной категории через обычный путь.

**Не трогаем.** `Controller` и `controllerService`: контроллер ввода дома
остаётся отдельной сущностью. Потолок решения — две сущности «источник данных»
живут параллельно; объединять после месяца стабильной работы универсального пути.

### 3.3. Тревоги

**Доработка, без дробления.** `alertService` в 1829 строк — самый большой модуль,
но бэклог прямо запрещает его спекулятивный рефакторинг, и до приёмки это правило
остаётся в силе. Делается ровно то, что бэклог допускает (N-28):

- четыре существующие проверки и подписки на события выносятся в
  `alert/detectors/` без изменения поведения;
- рядом добавляется один новый детектор — «канал, сравнение, значение,
  N секунд» для универсальных устройств;
- `alertGates`: проверка устойчивости, сейчас полная только для протечки,
  получает реализацию для универсальных каналов.

**`AlertRule` и редактор правил.** Правило получает необязательные поля «тип
устройства» и «канал». Существующие восемь правил не меняются.

**Не трогаем.** `alertVerificationService`, повторное открытие, подавление,
модели очереди. Новые типы тревог проходят через них без правок.

### 3.4. Интеграция с УК

**Доработка.**

- **`uk/alertForwarder`.** В тело события добавляются сведения об устройстве и
  ссылки `uk_elevator_id`, `uk_asset_id`, если устройство к ним привязано.
  Поля необязательные, старый формат остаётся допустимым.

**Новое.**

- Приём объявленного отключения от УК: вебхук, который создаёт запись
  `AlertSuppression` на заданное окно. Модель подавления уже существует.

**Не трогаем.** Outbox и его воркер, проверку подписей, обработку статусов
заявок, синхронизацию домов.

### 3.5. Вход и права

**Доработка.**

- **`middleware/auth`.** Второй способ установить пользователя: подписанные
  заголовки от edge. Включается `AUTH_MODE=uk`. Права приходят от УК и
  сопоставляются с действиями: просмотр, управление тревогами, команды.
- **Маршруты тревог.** Принятие, закрытие и подавление сегодня закрыты
  `isAdmin`. Переводятся на право управления тревогами, иначе диспетчер не
  сможет работать. Это же закрывает открытое решение S-AUTH-9.

**Вывод в запасной режим.** `authService`, `authController`, `totpService`,
`AccountLockout`, страница входа. Код не удаляется: он нужен для
`AUTH_MODE=local` — аварийного входа и поставки без УК. Развивать его дальше
не планируется.

### 3.6. API для интерфейса

**Доработка.** Лента тревог: постраничная выдача, фильтры по серьёзности,
статусу и дому, номер связанной заявки в ответе.

**Новое.**

- Сводка по объекту одним запросом: текущие значения, состояние устройств,
  открытые тревоги, последние заявки.
- Показания за период с автоматическим выбором уровня хранения.
- Отчёт за период по дому.
- Команды: постановка в очередь, статус, журнал.

Все ответы — в принятом конверте `sendSuccess` / `sendError`.

### 3.7. Интерфейсы

**Новое — раздел «Мониторинг» в панели УК** (`frontend/src/pages/monitoring/`):
лента тревог, карта, карточка объекта, отчёт. Стек и дизайн-система — те же,
что у остальной панели; новая зависимость одна — библиотека карты.

**Вывод.**

- **Карта InfraSafe** (`script.js`, `map-layers-control.js`). Остаётся публичным
  демо на infrasafe.uz. Правки только косметические: баннер, логотип, футер.
  Новые слои и функции сюда не добавляются.
- **Вход** (`login.js`, `admin-auth.js`) — вместе с локальным режимом.

**Доработка рядом, не внутри — `admin.js`.** Файл в 4003 строки при пороге 4500.
Вкладки «Устройства» и «Шлюзы» пишутся отдельными файлами и подключаются к
странице, а не дописываются в монолит. Сама админка остаётся инструментом
настройки и до приёмки в панель УК не переносится.

**Лендинг.** Без изменений.

### 3.8. Периметр и выкатка

- Оба конфига nginx: проверка пользователя у УК перед запросом к API
  InfraSafe, срезание входящих заголовков с правами, новые пути в списке
  разрешённых, тайлы карты в политике содержимого для `/uk`.
- Compose: сервисы брокера и моста. `update-production.sh`: мост пересобирается
  вместе с приложением, проверка живости моста после выкатки.
- Наблюдаемость (отдельный репозиторий): молчание устройства, задержка моста,
  длина очереди outbox.

### 3.9. Панель УК

- **Проверка входа для edge.** Точка, которая по куке сотрудника отвечает, кто
  он и какие у него права. Права `monitoring.view`, `monitoring.manage`,
  `monitoring.control` в существующей системе ролей.
- **`inbound_alert` и «Лифты».** Событие от датчика лифта меняет статус в
  карточке лифта. Модуль нужно сначала включить на проде.
- **Табло жителей и «Отключения».** Подтверждённая авария публикуется жителям
  дома; объявленное отключение уходит в InfraSafe как окно подавления.
- **Реестр ассетов.** Не входит в этот план как разработка: слой на карте
  появится, когда реестр будет на проде.

## 4. Зависимости

```
контракт (0.2) ─┬─▶ мост (1.3) ──▶ прогон (1.4) ──▶ пилот
                └─▶ модель устройств (2.1) ─┬─▶ правила каналов (2.2) ──▶ автостатус лифта (4.3)
                                            ├─▶ здоровье устройств (2.3)
                                            └─▶ админка устройств (2.4)
секции и свёртки (2.5) ──▶ графики в карточке (3.4) ──▶ отчёт (4.1)
единый вход (2.6) ──▶ каркас раздела (3.1) ──▶ лента (3.2), карта (3.3), карточка (3.4)
права на тревоги (2.6) ──▶ принятие тревоги из ленты (3.2)
```

Два узких места: контракт телеметрии и единый вход. Первый держит весь приёмный
контур, второй — весь новый интерфейс. Оба начинаются раньше остального в своём этапе.

## 5. Чего не делаем до приёмки

| Что | Почему |
|---|---|
| Перенос движка тревог на Python | Месяцы работы без пользы для пользователя, риск перед приёмкой |
| Дробление `alertService` сверх выноса детекторов | Запрет бэклога; ядро покрыто тестами и проверено аудитами |
| Дробление `admin.js` и `script.js` | Нет модульного графа; новые экраны пишутся в панели УК |
| Перенос админки в панель УК | Ею пользуется один администратор; операторам она не нужна |
| Объединение `metrics` и `device_readings` | Меняет вход всех существующих проверок |
| Объединение `controllers` и `devices` | То же; после месяца работы универсального пути |
| Удаление локального входа | Нужен как аварийный и для поставки без УК |
| Вторая карта в панели УК для ассетов | Карта одна, ассеты — слой |

## 6. После приёмки

По убыванию пользы:

1. Объединение путей показаний и сущностей «контроллер» и «устройство».
2. Перенос настройки (дома, трансформаторы, линии, правила) из `admin.html` в
   панель УК; после этого `admin.js` удаляется целиком.
3. Команды для фонтана и насосных; расписания освещения.
4. Показания счётчиков с устройств в «Учёт ресурсов» УК.
5. Уборка: `trash/` в индексе, неиспользуемые batch-маршруты, мёртвые методы,
   описание API.
6. Вынос edge-nginx в отдельный репозиторий по образцу `profk-observability`.
