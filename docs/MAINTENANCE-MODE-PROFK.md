# Режим обслуживания ProFK

Как выключить сайт profk.uz и как включить его обратно.

Реализация — `nginx-config/nginx.profk.conf`, блок «режим обслуживания»;
страница — `frontend-html/maintenance.html`.

## Две команды

```bash
ssh profk 'cd /opt/infrasafe && ./scripts/profk-maintenance-on.sh'    # выключить
ssh profk 'cd /opt/infrasafe && ./scripts/profk-maintenance-off.sh'   # включить
```

Каждый скрипт сам проверяет результат запросом к сайту и говорит, получилось
или нет. Reload nginx не нужен, деплой не нужен, конфиг править не надо.

Под капотом это наличие одного файла — `frontend-html/.maintenance`. Если
скриптов под рукой нет, то же самое руками:

```bash
touch /opt/infrasafe/frontend-html/.maintenance   # выключить
rm -f /opt/infrasafe/frontend-html/.maintenance   # включить
```

Проверить состояние:

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://profk.uz/     # 503 = выключен
```

Переключение мгновенное: nginx делает `stat()` на каждый запрос, а
`open_file_cache` в этом конфиге выключен — следующий же запрос видит новое
состояние.

## Что выключается, а что продолжает работать

Выключается всё, что видит посетитель: главная, дашборд УК (`/uk/*`), карта,
админка, `/api/*`.

Продолжает работать — намеренно, и это не настройки, а предохранители:

| Путь | Почему не гаснет |
|---|---|
| `/uk/api/v1/access/*`, `/uk/ws/v1/access/*` | **Контроль доступа УК — турникеты и двери.** «Выключить сайт» и «остановить проходную» — разные действия, и второе не должно случаться заодно с первым |
| `/health` | По нему живут мониторинг и byte-verify деплоя. Погасив его, мы ослепили бы себя же |
| `/.well-known/*` | Обновление TLS-сертификата (ACME) |
| `/brand/*` | Favicon самой страницы-заглушки |

Если контроль доступа когда-нибудь понадобится остановить осознанно — это
делается остановкой его контейнера, а не флагом сайта.

## Почему 503, а не 200 и не 404

503 + `Retry-After` — единственный код, который для поисковика значит
«вернусь позже»: страницы остаются в индексе. Заглушка с кодом 200 подменила
бы содержимое сайта в поисковой выдаче, 404 — выбросил бы его из индекса.

Побочный эффект, принятый осознанно: обработчик перехватывает **любой** 503 на
площадке, включая настоящий отказ приложения. Для посетителя это верно
(сообщение то же самое), а оператор смотрит не на страницу, а на `/health` и
мониторинг — они из режима исключены. У `/uk/` свой
`error_page 502 503 504 /uk-unavailable.html` внутри location, и он главнее.

## Правка текста страницы

`frontend-html/maintenance.html`. Каталог примонтирован в nginx
directory-mount'ом (B-002), поэтому достаточно `git pull` на хосте — reload не
нужен.

Правило вёрстки жёсткое: **ни одного внешнего запроса** — ни CSS, ни шрифтов,
ни скриптов. Страница показывается ровно тогда, когда всё остальное отдаёт 503,
и любая внешняя зависимость обернётся пустым экраном. Это же караулит тест
`tests/jest/unit/maintenanceFlag.test.js`.

Контакты намеренно не заполнены — в HTML лежит закомментированный блок,
впишите телефон и удалите комментарий.

## Первое включение

Механизм заработает только после того, как правка конфига приедет на хост:

```bash
ssh profk 'cd /opt/infrasafe && git pull --ff-only \
  && docker exec infrasafe-nginx-1 nginx -t -c /etc/nginx/custom/nginx.profk.conf \
  && docker exec infrasafe-nginx-1 nginx -s reload -c /etc/nginx/custom/nginx.profk.conf'
```

Это конфиг-only изменение: `update-production.sh` не нужен, пересборка образа не
нужна. Пока флага нет, поведение площадки не меняется ничем — можно доставить
заранее, и «в моменте» останется только запустить скрипт.

Если скрипт `…-on.sh` сообщил, что сайт всё ещё отвечает 200 — это ровно тот
случай: конфиг с гейтом до хоста не доехал.

## Как проверено (16.08.2026, локально)

Настоящий `nginx.profk.conf` поднимался в контейнере `nginx:alpine` со стабами
вместо апстримов (все `proxy_pass` идут через переменные, поэтому конфиг
стартует без реальных сервисов):

- `nginx -t` на настоящем конфиге — успешно;
- оба скрипта запущены **без изменений** в контейнере, где `profk.uz`
  резолвится на локальный edge: `on` → «сайт выключен (503)», `off` → «сайт
  включён (302)»;
- таблица выше воспроизведена целиком: при выключенном сайте `/`,
  `/uk/resident-board`, `/api/*` и `/admin.html` отдают 503, а контроль
  доступа, `/health` и `/brand/` — 200;
- ответ заглушки: `HTTP/2 503`, `Retry-After: 3600`, `Cache-Control: no-store`
  и полный набор security-заголовков (HSTS, CSP и остальные).

Оговорка честности: замеры на macOS, где bind-mount идёт через FUSE-слой. Там
примерно раз из пяти **первый** запрос сразу после снятия флага ещё отдавал
503, следующий — норму (поэтому `…-off.sh` перепроверяет один раз). На
Linux-проде такого слоя нет, эффекта не ожидается.
