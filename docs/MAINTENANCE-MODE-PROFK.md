# Режим обслуживания ProFK (kill-switch площадки)

Как за секунду погасить сайт profk.uz и как вернуть его обратно.
Реализация — `nginx-config/nginx.profk.conf`, блок «режим обслуживания»;
страница — `frontend-html/maintenance.html`.

## Команды

```bash
# ПОГАСИТЬ сайт (карта, админка, API, дашборд УК).
# Контроль доступа продолжает работать.
ssh profk 'touch /opt/infrasafe/frontend-html/.maintenance'

# ВЕРНУТЬ.
ssh profk 'rm -f /opt/infrasafe/frontend-html/.maintenance'

# Проверить состояние.
curl -s -o /dev/null -w '%{http_code}\n' https://profk.uz/          # 503 = погашено
ssh profk 'ls -a /opt/infrasafe/frontend-html | grep maintenance'
```

Reload nginx не нужен, деплой не нужен, конфиг править не надо. Проверка
флага — `stat()` на каждый запрос, `open_file_cache` в этом конфиге выключен,
поэтому следующий же запрос видит новое состояние.

## Что гаснет и что живёт

| Путь | `.maintenance` | `.maintenance-all` |
|---|---|---|
| `/`, `/uk/resident-board`, весь дашборд УК | 🔴 503 | 🔴 503 |
| `/api/*` (карта, метрики, вебхуки УК) | 🔴 503 | 🔴 503 |
| `/uk/api/v1/access/*`, `/uk/ws/v1/access/*` — **контроль доступа** | 🟢 работает | 🔴 503 |
| `/health` — мониторинг и byte-verify деплоя | 🟢 всегда | 🟢 всегда |
| `/.well-known/*` — обновление сертификата | 🟢 всегда | 🟢 всегда |
| `/brand/*` — favicon самой заглушки | 🟢 всегда | 🟢 всегда |

**Почему два флага.** Под `/uk/api/v1/access/` живёт контроль доступа УК —
турникеты и двери. Погасив его вместе с сайтом, можно физически запереть людей
снаружи или внутри. Поэтому обычный `.maintenance` его не трогает, а «совсем
всё» вынесено в отдельный флаг, который нельзя поставить случайно:

```bash
ssh profk 'touch /opt/infrasafe/frontend-html/.maintenance-all'   # ВКЛЮЧАЯ двери
ssh profk 'rm -f /opt/infrasafe/frontend-html/.maintenance-all'
```

Флаги независимы: `-all` работает и сам по себе. Снимать нужно тот, который
поставлен (или оба сразу — `rm -f …/.maintenance{,-all}`).

## Почему 503, а не 200 и не 404

503 + `Retry-After` — единственный код, который для поисковика значит
«вернусь позже»: страницы остаются в индексе. Отдать заглушку с кодом 200
значило бы подменить содержимое сайта в поисковой выдаче, 404 — выбросить его
из индекса.

Побочный эффект, принятый осознанно: обработчик перехватывает **любой** 503 на
площадке, включая настоящий отказ приложения. Для посетителя это верно
(сообщение то же самое), а оператор смотрит не на страницу, а на `/health` и
мониторинг — они из режима исключены. У `/uk/` свой
`error_page 502 503 504 /uk-unavailable.html`, объявленный внутри location, и
он остаётся главнее.

## Проверено (14–16.08.2026, локально на реальном конфиге)

Конфиг поднимался в контейнере `nginx:alpine` со стабами вместо апстримов:

- `nginx -t` на настоящем `nginx.profk.conf` — успешно;
- матрица из таблицы выше воспроизведена целиком, включая живой контроль
  доступа при `.maintenance` и его гашение при `.maintenance-all`;
- ответ заглушки: `HTTP/2 503`, `Retry-After: 3600`, `Cache-Control: no-store`,
  полный набор security-заголовков (HSTS, CSP, X-Frame-Options и остальные);
- переключение в обе стороны — десятки миллисекунд, без reload.

Оговорка честности: замеры сделаны на macOS, где bind-mount идёт через
FUSE-слой. Там примерно один раз из пяти **первый** запрос сразу после `rm`
ещё отдавал 503, следующий — уже норму. На Linux-проде такого слоя нет
(нативный bind-mount), поэтому эффекта не ожидается; но если после снятия
флага первый запрос показал заглушку — обновите страницу, прежде чем
что-то чинить.

## Правка текста страницы

`frontend-html/maintenance.html`. Каталог примонтирован в nginx directory-mount'ом
(B-002), поэтому достаточно `git pull` на хосте — reload не нужен.

Правило вёрстки жёсткое: **ни одного внешнего запроса** — ни CSS, ни шрифтов,
ни скриптов. Страница показывается ровно тогда, когда всё остальное отдаёт 503,
и любая внешняя зависимость обернётся пустым экраном.

Контакты в странице намеренно не заполнены — в HTML лежит закомментированный
блок, впишите телефон и удалите комментарий.

## Первое включение

Механизм заработает только после того, как правка конфига приедет на хост:

```bash
ssh profk 'cd /opt/infrasafe && git pull --ff-only \
  && docker exec infrasafe-nginx-1 nginx -t -c /etc/nginx/custom/nginx.profk.conf \
  && docker exec infrasafe-nginx-1 nginx -s reload -c /etc/nginx/custom/nginx.profk.conf'
```

Это конфиг-only изменение: `update-production.sh` не нужен, пересборка образа
не нужна. Пока флагов нет, поведение площадки не меняется ничем.
